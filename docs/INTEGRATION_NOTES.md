# Integration Notes

- This workspace owns Developer 2 products: Cooperative, Ajo / Esusu, Target Savings, Revenue, and Agent Network.
- Mobile and web live under `mobile/` and `web/`, matching the documented frontend layout.
- The shells do not include shared authentication, global banking navigation, or shared design-system packages. Cooperative creation has an isolated API repository.
- The cooperative-create repository uses the documented POST /cooperatives request shape, but the UI currently prevents submission for both types: registered-document upload and informal officer identity are not covered by complete contracts. It reads an access token from secure storage under the local key access_token and takes its base URL from the API_BASE_URL Dart define. Replace this with the shared SessionManager and ApiClient during integration.
- Mobile API calls now use a shared Dio-based ApiClient that attaches the bearer token from secure storage and adds X-Request-Id; refresh behavior and the storage key must be reconciled with the shared SessionManager.
- Cooperative contribution payment, loan request, guarantor selection, guarantee response, loan detail, and repayment routes are present as blocked states until financial terms, eligibility, and response schemas are defined and the extracted PIN contract is integrated through shared security services.
- Cooperative registered-document upload is not implemented because the create response ID and file upload/storage contract are unspecified.
- The cooperative dashboard is layout-only. Its figures and activity panels remain unpopulated because the OpenAPI success response has no schema and there is no running backend.
- The mobile Cooperative home follows the assigned Stitch hierarchy for a summary, membership list, primary create/join actions, and explainer; it shows unavailable values instead of Stitch sample balances because the list response is schema-less.
- The cooperative join-code screen does not call the preview or membership endpoints until the preview response schema allows it to show the required group details before requesting membership.
- The mobile cooperative overview route accepts a cooperative ID, but it remains unavailable until the overview response is defined; the list/create contracts also do not currently provide an ID to navigate here.
- The mobile contributions route is present, but plan/dues data and payment are unavailable until their response schemas are published and PIN verification is integrated through shared security services.
- The mobile shares route is present, but holdings, certificate and history remain unavailable until GET /cooperative/shares/me defines its response and certificate details.
- The mobile loans overview route is present, but eligibility has no response schema and no member loan-list operation is specified; the loan request entry stays disabled until eligibility and limits are available.
- The mobile community hub is layout-only. Announcements have no response schema, while meetings have no read or RSVP endpoint.
- The web organizer hub has announcement and meeting forms, but publishing/scheduling awaits the shared web session adapter; meeting lists, attendance, and minutes upload are unsupported by the API.
- The web cooperative audit route has filter/export controls without event data until audit-list and export schemas are defined. Verification shows unavailable states because document listing, upload/storage, trust level, and unlocked-limit contracts are missing.
- The mobile cooperative leave screen is present, but submission remains disabled until obligations and settlement can be reviewed and PIN verification is integrated through shared security services.
- The mobile admin-approvals screen has Join requests, Loans, and Withdrawals tabs; queue data/actions remain unavailable until list response schemas and a withdrawals list operation are defined.
- The mobile statement screen has date-range and section tabs, but records and PDF download remain unavailable until the statement response and file-delivery contracts are defined.
- The web cooperative member directory is layout-only. Its filters, invite action, records, and member actions remain unavailable until GET /cooperative/members publishes a response schema.
- The web cooperative join-request queue is layout-only. Approve/reject controls remain disabled until the list response schema exposes applicant data and request IDs.
- The web Plans and Arrears screen has its management layout, but records, plan creation, and export remain unavailable pending response schemas, category allocation details, an export contract, and the shared web session/API adapter.
- The web loan-application queue and review panel are layout-only until the admin queue response defines application, member history, guarantor, schedule, and dual-control fields; decision actions remain disabled.
- The web loan portfolio is layout-only because the API has no cooperative-wide loan-list endpoint and does not expose recovery notice status; recovery remains disabled.
- The web Shares and Dividends screen is layout-only until policy-read, admin-holdings, dividend preview/run-state, and web session contracts are defined.
- The web Rules and Settings screen has category sections and a version-history area, but editing/submission remains unavailable until rules and version-history contracts are typed.
- The web Admins and Roles screen is layout-only; roster, role assignments, and succession remain unavailable until admin-list and permission-catalog contracts are published.
- The web Ledger and Reports screen has report choices and date/export controls, but remains unavailable until response and file-delivery formats are specified.
- The web Withdrawals screen is layout-only; verified destinations, pending/history lists, cooling-off state, and shared PIN authorization are not available.
- Ajo home and invite-code entry are implemented as UI slices. The circle list and invite preview remain unavailable until their GET response schemas are defined; the preview action is disabled and no join request is sent.
- The Ajo web organizer dashboard is layout-only. Circle status, pot, payout rounds, members, and invite actions remain unavailable until the Ajo detail response and circle identifier contract are defined.
- Mobile Ajo creation submits the documented request and shows the submitted terms after success, but the API does not return a circle ID, so it cannot continue to invite members. Mobile circle overview, schedule, and pay routes are placeholders pending typed detail/schedule responses, circle-to-tenant mapping, and shared PIN security integration.
- If Ajo circle creation returns a network error, the mobile screen now treats the result as unknown and prevents an in-screen resubmission. The API has no idempotency key or request-status lookup, so users are told to verify with their service provider before submitting the same details again.
- Mobile Ajo protection, guarantee, payout-order, round, member, and cycle-summary routes are placeholders pending typed responses and documented tenant/authorization context.
- The mobile Ajo invite screen is blocked because the API defines code preview and join, but not an operation for organizers to generate or retrieve a shareable invite code.
- The mobile Ajo report form is present, but submit and evidence attachment remain disabled until circle-to-tenant mapping and evidence-upload contracts are defined.
- Target Savings home and create screens use the extracted front-end contract set. The home cannot load real goals without the list response schema. The create flow verifies PIN through `/auth/pin/verify` and submits `/targets` with an idempotency key. Its success screen shows the submitted setup details, while the confirmation remains generic because the create response does not return a goal ID or created-goal representation.
- Target Savings auto-save setup verifies PIN and submits the documented frequency, amount, and start date with consent and an idempotency key. Its success screen now shows those submitted schedule values; a reach-goal projection remains unavailable until the service publishes calculation semantics and response fields.
- `mock-api/` contains a local Target Savings contract subset for request/success-flow development. It returns only the empty response bodies and status codes declared in the product spec, plus the documented core PIN-token shape. It does not provide goal, balance, or projection fixtures; see its README for run instructions and limits.
- Target Savings home also has an opt-in, read-only demo display copied from the supplied Stitch sample values. It is labeled as design data and does not act as an API response; normal mode continues to show the documented unavailable state.
- The opt-in `DEVELOPER_TWO_DESIGN_DEMO` mode previews the supplied design screenshots for 61 mobile and 26 web inventory routes. It is a visual reference only; missing API response schemas and shared session/PIN/security integration remain blockers. See [DESIGN_DEMO_MODE.md](DESIGN_DEMO_MODE.md).
- Automatic saving is configured by a separate typed operation (`frequency`, `amountKobo`, `startDate`). The create request's `autoSave` is unconstrained, so the create flow explains that schedule setup is unavailable and does not present a toggle that could imply deposits were enabled. Schedule setup still requires a goal ID from the create response.
- The `/targets/:id/auto` screen now submits the documented schedule request after explicit consent and PIN verification. Its API response has no body; the screen shows a generic success and does not invent a schedule preview or goal balance.
- The isolated Target Savings PIN pad stores digits only in widget memory and sends them directly to the documented verification endpoint. Platform screenshot protection and the shared `SecurityService` are still needed before integration; see [REFERENCE_SOURCES.md](REFERENCE_SOURCES.md).
- Target goal detail, withdrawal, edit, projection, and rules routes remain blocked states. Typed list/detail/quote responses are missing; the extracted core PIN contract still needs shared security integration before remaining protected actions are enabled.
- Target top-up now submits the documented `amountKobo` request with PIN verification and an idempotency key. The main-account balance and posted activity remain unavailable because the related read responses are not typed.
- Agent Network mobile routes are present as blocked screens. Endpoints define several request bodies, but success responses are schema-less; recipient verification, balances, fee/limit details, cash-out status, and shared session/PIN handling remain prerequisites for enabling money actions.
- Agent Network backoffice application, float/reconciliation, and configuration routes are present as blocked pages. Their list/read models and dual-approval flow need backend contracts before review or configuration actions can be enabled.
- Revenue mobile bill and field-collector routes are present as blocked screens. API success responses do not define the bill, payer, fee, payment, or receipt data, and payment actions require shared session/PIN integration.
- Revenue mobile navigation no longer points to sample bill or payer IDs. Detail, dispute, abuse-report, and cash-record routes require a real record reference before they can be opened from the UI.
- Revenue collector web dashboard, items, payers, collections, field, settlement, reports, and verification routes are present as blocked pages. The current Revenue API does not provide typed responses, and collector tenant/session setup must be reconciled with the shared frontend shell.
- Before integration, align route prefixes, navigation entry points, design tokens, auth/session handling, API client conventions, i18n catalog ownership, and feature flag source with Developers 1 and 3 and the backend team.
- The web product landing labels Cooperative, Ajo, and Revenue links as previews because they use sample workspace keys; replace these keys with the authenticated workspace selector during integration. Target Savings currently has mobile screens only.
- No bank partner name, logo, or icons are included.
