# Specification Gaps

| Gap | Impact | Recommended resolution |
|---|---|---|
| No shared application repository or core frontend shell was present in this workspace. | Auth, global navigation, and shared components must be reconciled at integration. | Agree shared repository layout and ownership of shared foundations before merging. |
| No running backend API or behavior-complete mock server is available in this workspace. A local Target Savings contract mock now covers documented request shapes and empty success responses only. | Product read models, financial state, and undocumented success/error behavior cannot be exercised end to end. | Use the backend team's versioned API contract and agreed service environment; expand the local mock only when response schemas and behavior are specified. |
| Product OpenAPI files document many success responses without response schemas, including the cooperative admin dashboard. | Frontend cannot safely type the server response or render real dashboard values from these contracts. | Backend should publish response schemas; keep these views in loading/empty/error states until then. |
| Cooperative list and invite-code preview success responses have no schemas. | The cooperative home cannot safely display group summaries and the join flow cannot show the required cooperative preview before requesting membership. | Backend should add response schemas for GET /cooperatives and GET /cooperatives/by-code/{code}. |
| Cooperative member overview success response has no schema. | Member balances, verification status, next due, arrears and quick-action context cannot be populated safely. | Backend should define GET /cooperative/overview response fields, including the cooperative ID-to-tenant context and member summary fields. |
| Cooperative plan and dues list success responses have no schemas; manual contribution requires a PIN token. | Plan cards, due amounts, payment history and a safe payment confirmation cannot be implemented end to end. | Backend should define GET /cooperative/plans and GET /cooperative/dues responses; integrate the extracted core PIN contract through the shared security service. |
| Cooperative member share response has no schema. | Share count, unit price, max-share progress, certificate and history cannot be displayed safely. | Backend should define GET /cooperative/shares/me response fields and certificate delivery details. |
| Cooperative share policy has no read endpoint, admin holdings have no list endpoint, and dividend runs lack preview/list/status operations. | Admins cannot review current policy or holdings, calculate an allocation, or safely operate the approval/post stages. | Add policy-read, admin-holdings, and dividend preview/list/status contracts, including dual-control and PIN behavior. |
| Cooperative rules GET has no response schema and rule drafts accept an unconstrained object; version history, diff, and notice-period behavior are unspecified. | Settings cannot safely display active values, validate drafts, or explain when changes take effect. | Define typed rule categories, active/draft/version-history responses, diff format, effective-date and notice-period semantics. |
| Cooperative admins have no list endpoint, and invite role/permission fields have no enumerated catalog. | Admin assignments and minimum-admin checks cannot be safely displayed or changed. | Define an admin roster response and role/permission catalog, including succession eligibility and approval requirements. |
| Cooperative report endpoint has no response schema, content type, or file-delivery contract; `format` is not enumerated. | Trial balance, summaries, statements, AGM pack, and PDF/CSV export cannot be rendered or downloaded reliably. | Define report types, response models/content types, and supported export formats. |
| Cooperative withdrawals have no pending/history list or verified-destination read contract; create and approve operations require PIN authorization. | Admins cannot select a verified destination, review pending approvals/cooling-off, or safely submit and approve withdrawals. | Define verified destinations, pending/history responses, cooling-off/objection states, and integrate PIN authorization through the shared security service. |
| Cooperative loan eligibility response has no schema, and there is no member loan-list operation. | Eligibility, limits, active loans, guarantees and a safe loan-request entry cannot be presented. | Define GET /cooperative/loans/eligibility response fields and a member loan-list operation with response schema. |
| Cooperative loan detail, repayment schedule, guarantor eligibility, and guarantee response/action fields are not fully typed. | Members cannot compare repayment terms, confirm guarantee liability, or submit reliable loan and contribution payments. | Define loan detail/schedule and guarantee models, guarantor eligibility, and payment confirmation responses; integrate the extracted PIN API through the shared security service. |
| Cooperative announcements have no response schema; meetings have no list operation or RSVP operation. | Member announcement and meeting views cannot show records, minutes, or collect attendance responses. | Define GET /cooperative/announcements response fields, meeting list/details, and RSVP request/response contracts. |
| Cooperative admin hub has no meeting read/edit, attendance/RSVP, or minutes upload operations; announcement list response is schema-less. | Admins cannot follow up on scheduled meetings or review published announcements and attendance. | Define announcement responses and meeting list, update, attendance/RSVP, and minutes upload contracts. |
| Cooperative audit events have no list or export response contract; cooperative verification has no document, trust-level, limit, or upload contracts. | Admins cannot inspect before/after actions, export a reliable audit trail, or review and submit cooperative verification documents. | Define paginated audit events and export formats, document status and rejection responses, trust levels and unlocked limits, and document upload/storage operations. |
| Agent Network success responses are schema-less across agent dashboard, cash-in/out, float, history, day-end, locator, applications, feedback, and backoffice operations; shared session/security integration is absent. | Frontends cannot verify recipients, show fees/limits or balances, review cash-out codes, confirm money movement, reconcile, or manage agent applications safely. | Define response schemas, fee and limit lookups, cash-out expiry/confirmation behavior, supported float methods, and integrate the extracted PIN API through shared session/security services before enabling actions. |
| Revenue and Dues list/detail, fee quote, receipt, dashboard, payer, payment, and report success responses are schema-less; collector web tenant mapping and shared session/security integration are absent. | Customers and collectors cannot verify bills, fee totals, payer identity, payment states, or receipts before completing payment or collection flows. | Define typed responses and collector tenant context, enumerate fee/payment states, and integrate shared authentication and the extracted core PIN contract before enabling payments. |
| Agent backoffice float/reconciliation has no list endpoint; commission/limits have a write endpoint but no read schema or defined second-approver workflow. | Operations cannot monitor aggregate float, resolve day-end variances, or safely review and approve configuration changes. | Define operational list/read models and variance semantics, then specify the dual-control proposal and approval lifecycle. |
| Cooperative leave has no obligation/settlement read contract and requires an `X-Pin-Token`. | Members cannot review loans, guarantees, or expected settlement before submitting a leave request. | Define leave eligibility/settlement and obligation responses and integrate PIN authorization through the shared security service. |
| Cooperative statement success response has no schema, and no PDF delivery format or operation is defined. | Statement tabs cannot render records or export a reliable PDF. | Define statement response shape, date-filter semantics, and a downloadable statement format or export endpoint. |
| Cooperative member-list success response has no schema. | The admin member directory cannot safely render records, status filters, pagination, or member actions. | Backend should define GET /cooperative/members response fields and pagination behavior. |
| Join-request and loan-application queues have no response schemas; withdrawals have no pending-list operation. | Admin approval tabs cannot show review details or safely submit decisions against specific records. | Define queue response schemas and a pending-withdrawals list operation; document decision/dual-control state and PIN authorization. |
| Cooperative loan portfolio has no list endpoint, and recovery does not expose or query the required notice state. | Admins cannot see active loans, overdue status, guarantors, or know whether recovery is permitted. | Define a paginated loan-portfolio response and recovery-notice state/eligibility contract. |
| Cooperative arrears has no response schema; plan `categoryAmounts` is unconstrained; no export format is defined. | The web compliance table, category allocations, and export cannot be completed. | Define arrears fields, typed category allocation keys, and export response format. |
| Ajo circle creation, circle listing, and invite-code preview responses have no schemas. | A newly created circle cannot be opened or displayed safely, and members cannot see the required invite preview. | Backend should define circle identifiers and response models for create, list, and by-code preview operations. |
| Ajo circle creation has no idempotency-key parameter or request-result lookup. | After a network failure, the client cannot tell whether creation succeeded; retrying may create a duplicate circle. | Support idempotent create requests and/or provide a way to query the result by request ID. |
| No Ajo invite-code generation/share operation is defined. | Organizers cannot retrieve a valid invite code to share from the circle screen. | Define an authorized invite-code operation, code lifecycle, and response fields. |
| Ajo circle detail, payout schedule, and contribution responses have no schemas; their endpoints also require a tenant ID that is not available from the mobile route. | Members cannot review circle or round details, verify a payout slot, or confirm a contribution amount and due round safely. | Define the response schemas and document the circle-to-tenant mapping; integrate the extracted core PIN API through the shared security service before enabling payments. |
| Ajo protection status, guarantee detail, payout-order, round-detail, member-roster, and cycle-summary responses are not typed. Some actions also require PIN authorization and tenant context. | Members cannot compare protection options, act on guarantee requests, confirm a payout order, or review round/member/cycle state safely. | Publish response schemas and tenant mapping for these views, plus authorization requirements and typed results for protection and payout-order actions. |
| Ajo report requires `X-Tenant-Id`, while the `/ajo/:id/report` route does not define how its circle ID maps to a tenant; evidence upload has no contract. | A report cannot be sent with the correct tenant context or attachments. | Define circle/tenant context for report routes and evidence upload request, storage, and response contracts. |
| Cooperative creation returns no documented cooperative ID, and the follow-up document upload flow has no file upload contract. | Registered cooperative setup cannot complete its required certificate and bye-laws submission. | Backend should specify the creation response ID and document upload/storage flow. |
| Informal cooperative setup requires officer identity details in the flow, but POST /cooperatives has no identity fields or identity-verification operation. | Informal creation cannot follow the approved setup flow without inventing identity data or assuming it comes from another service. | Define whether officer identity comes from core KYC or add a documented identity-verification step and request contract. |
| The extracted core OpenAPI defines PIN verification, and Target Savings defines the create request and a separate typed auto-save operation. The create request's `autoSave` is still unconstrained and its 201 response does not return a goal ID. | The frontend can authorize and create a goal, but cannot safely include an automatic schedule in that request or navigate to its new detail screen. | Type `autoSave` in the create request or create the goal first and then call the typed auto-save operation; return the new goal ID from goal creation. |
| Target savings list, detail/history, withdrawal quote, what-if, and rules responses have no schemas. | Mobile cannot show balances, transactions, projections, fees, withdrawal quotes, or maturity/limit rules safely. | Define typed responses and calculation semantics for each read/quote operation before rendering financial amounts or enabling confirmations. |
| The core API has no operation to query the result of an idempotent request after the app is closed or a network outcome is unknown. | An in-session Target Savings retry reuses its idempotency key, but a process restart cannot safely reconcile whether goal creation succeeded. | Define an idempotency-result lookup or provide a session-safe reconciliation method before relying on retry across app restarts. |
| The extracted core OpenAPI defines login and refresh token exchanges, but this isolated workspace's ApiClient reads its own `access_token` key and has no refresh interceptor. | Independent frontend modules cannot safely share token ownership or refresh an expired session. | Adopt the core frontend SessionManager and refresh behavior before integration. |
| Branding and design token references need reconciliation. | Avoids embedding unsettled identity or conflicting colors. | Use canonical shared DESIGN_TOKENS.json and keep unsettled branding configurable. |
