# Pay Am Small customer preview (first batch)

This additive feature package implements S-PAS-001 Marketplace home, S-PAS-002 Product detail, S-PAS-003 Plan setup, S-PAS-004 Plan summary and terms, S-PAS-005 My plans, S-PAS-006 Vault detail, S-PAS-007 Add Money, S-PAS-008 Withdraw, S-PAS-009 Deadline Decision, S-PAS-010 Order Tracking, and S-PAS-012 Vendor storefront. S-PAS-011 and later screens are outside these batches. It does not change the completed Merchant packages or previews.

## Structure

- `mobile/` contains host-injected Flutter presentation pages, display models, adapters, and focused widget tests.
- `preview/` is a separate non-production Flutter application with the eleven implemented screens registered, synthetic/unavailable fixtures, light/dark switching, and a persistent warning banner.

## Run the isolated preview

From `implementation/pay_am_small/preview`, run:

```powershell
flutter pub get
flutter devices
flutter run -d chrome
```

The preview includes Flutter Web configuration in `preview/web/`, uses the locally bundled CanvasKit and Inter assets, and runs in Chrome as an isolated, non-production app. To create a production-mode web build for verification, run `flutter build web --no-pub` from the same directory. To use an Android emulator instead, run `flutter run -d <android-device-id>`.

Use the top-right screen menu to open S-PAS-001 Marketplace home, S-PAS-002 Product detail, S-PAS-003 Plan setup, S-PAS-004 Plan summary and terms, S-PAS-005 My plans, S-PAS-006 Vault detail, S-PAS-007 Add money, S-PAS-008 Withdraw, S-PAS-009 Deadline decision, S-PAS-010 Order tracking, or S-PAS-012 Vendor storefront directly. The theme button switches light/dark mode. Tap a product, choose Price-lock, and continue to S-PAS-003; its quote leads to S-PAS-004. My Plans opens Vault Detail for the selected synthetic vault. S-PAS-006 links to Add Money and Withdraw; a host can expose Deadline Decision from the vault only when authoritative status allows it. The S-PAS-009 preview has no confirmed extension/refund terms, so both actions are unavailable. S-PAS-010 uses an empty synthetic order fixture with no generated shipment events, delivery code, vendor contact, product, or dates. Its order route is `/shop/orders/synthetic-order-001`. Problem reporting is unavailable because S-PAS-013 is not part of this batch. The synthetic top-up adapter acknowledges preview-only and changes no balance or payment state. Withdrawal confirmation remains unavailable because the preview has no approved quote terms. Auto-debit switching is acknowledged only by the local synthetic adapter and performs no real consent, PIN, account or debit operation.

## Contract gaps and omitted behavior

- `GET /pas/products` documents query parameters but no success response schema. `GET /pas/products/{productId}` also has no success response schema. The feature adapter therefore accepts host-mapped presentation models rather than defining wire DTOs.
- No vendor-profile/storefront endpoint exists, and the products endpoint has no vendor filter. `loadStorefront(vendorId)` is an explicit host adapter seam; no endpoint or response schema is assumed.
- Product image, rating/review count, verified/suspended state, delivery terms, locked-price terms, availability, and offered purchase options must be supplied by the host. Optional text is omitted if missing. No vendor guarantee, delivery SLA, stock quantity, rating, fee, schedule, or savings claim is generated by the feature.
- The feature exposes only Pay in full and Price-lock presentation options. Vendor-funded Credit is omitted and cannot be selected in this batch. This avoids enabling the PRD's open credit mode; it does not implement a credit decision or financing rule.
- The API has no payment-in-full purchase endpoint or product-image upload/delivery contract for these customer screens. The host owns any supported navigation/action binding.
- Price-lock Continue opens the plan setup flow. The isolated preview injects a synthetic plan adapter; quote facts, dates, and terms are labelled as preview-only and no network, PIN, plan, or payment operation runs.
- Stitch-only financial rules, vendor metrics and escrow/warranty claims are not treated as production behavior. The host owns the banking bottom navigation; the isolated preview renders a local five-tab shell, while taps on tabs outside this preview only explain that those sections are unavailable. The preview uses synthetic reference data under its persistent non-production notice.
- Inter is bundled from the font named in the approved Stitch HTML so typography does not depend on network access. Its SIL Open Font License is included beside the asset. See `preview/PREVIEW_IMAGE_ASSETS.md` for the font and image provenance.
- O-008 remains open: the shared token file marks brand colours as proposed. This feature continues using the existing workspace berry tokens and does not edit shared tokens.
- The isolated preview bundles preview-only copies of product/storefront images referenced by the official S-PAS-001, S-PAS-002 and S-PAS-012 Stitch HTML. They are local assets, not runtime network images or production catalog data. Image widgets retain theme-aware loading and failure fallbacks. See `preview/PREVIEW_IMAGE_ASSETS.md` for exact source paths and the S-PAS-012 vendor-image conflict.

### Plan API contract gaps

- `GET /pas/plans` and `GET /pas/plans/{planId}` have no success response schemas. S-PAS-005 and S-PAS-006 consume host-mapped `PasPlanListData` and `PasVaultDetail` view models; these are presentation contracts, not inferred API DTOs. The host must map plan group/status, server-computed totals/progress, dates, items, contribution history, and auto-debit display state from a confirmed backend response.
- `PUT /pas/plans/{planId}/auto-debit` requires `enabled`; `frequency` and `amountKobo` are optional, and its `200` response schema is absent. The detail UI changes only the enabled setting and sends only that documented field. The host owns PIN/consent authorization and `Idempotency-Key` / `X-Pin-Token` handling. Account selection, schedule editing, and returned state are not assumed.
- S-PAS-006 links to S-PAS-007 Add Money and S-PAS-008 Withdraw. Their host adapters remain responsible for authorization and idempotency headers; the preview performs no real money movement.
- S-PAS-005 light Stitch includes search/filter controls and a new-plan action; the approved UI spec and `GET /pas/plans` contract define no list-query/filter or new-plan action contract on this screen. Those controls are omitted rather than presented as working.
- The dark Stitch variants for S-PAS-005/006 use materially different structures and include additional claims/actions. This batch follows the light structure and applies the documented dark tokens to that same structure. Uncontracted inflation/price guarantees, account operations, share/options actions and financial claims are not implemented.

### Add Money and Withdraw contract gaps (Batch 4)

- `POST /pas/plans/{planId}/topups` documents `amountKobo`, `Idempotency-Key`, and `X-Pin-Token`, but has no success response schema. The Add Money adapter accepts host-mapped vault context and a request containing only `amountKobo`; the host owns PIN authorization and headers. No funding account selector, preset amount, fee, schedule impact, or payment method is fabricated. The preview top-up result is explicitly preview-only and does not mutate balances.
- The task-supplied withdrawal route is `POST /pas/plans/{planId}/withdraw`, while the Developer 3 OpenAPI copy lists `POST /pas/plans/{planId}/withdrawal`, body `{confirm: boolean}`, and no success schema. The functional description says quote-then-confirm but defines no separate quote endpoint or quote response fields. This route and response-contract conflict needs API-owner resolution. The UI adapter is injected and does not hardcode either URL.
- Withdrawal penalty, net proceeds, eligibility, confirmation/PIN sequencing, and locked-price consequences are not defined as API response fields or complete financial rules. The screen displays those values only when supplied by a host with confirmable terms, performs no calculation, and remains disabled in the synthetic preview because no supported quote exists. No synthetic withdrawal is sent or represented as completed.
- S-PAS-007/008 references depict account switching, preset amounts, fee/schedule effects, penalties and account-routing details. Those elements are omitted where the API/spec does not support them. Light and dark use the same screen hierarchy with theme tokens; preview fixtures and their amounts are synthetic only.

- `POST /pas/plans/quote` documents `productIds`, `mode`, optional `deadline`, and an `autoSave` object with unconstrained additional properties. The `autoSave` child schema is missing. The UI can request a `PRICE_LOCK` quote and optional date; automated scheduling is visibly unavailable and is not sent. Manual funding remains the supported selection.
- The quote endpoint has no `200` response schema. The feature therefore accepts a host-mapped `PasPlanQuote` containing quote ID, terms version, server-supplied facts, and full terms. A production host must map the actual response into this presentation model after the response contract is confirmed; no wire response field names are presumed.
- `POST /pas/plans` documents only `quoteId` and `termsVersion` in its body, requires `Idempotency-Key` and `X-Pin-Token`, and has no `201` response schema. The injected host adapter must run the host PIN flow and attach those headers before calling the endpoint. The UI assumes no plan ID or follow-on route.
- The UI specification includes a â€œterms version changedâ€ state, but no corresponding error code is listed in the API/error catalog. A host may map a confirmed backend error to that presentation state; otherwise the feature shows a generic error.
- The deadline validation depends on each vendorâ€™s committed lock window, but the API does not describe a window/discovery field. The selected date is sent to the quote service without a locally invented range; the server remains authoritative.
- The Stitch screens depict account selection, automated debit cadence/amounts, initial deposits, fee and penalty examples, and other financial figures. The current contracts do not define funding-account selection, `autoSave` fields, initial-deposit behavior, or quote response fields. Those controls/figures are not simulated as production behavior. Any shown quote facts and terms are supplied by the synthetic preview adapter and explicitly disclaim real rules.
- The `productIds` array supports multiple IDs, but the approved mobile batch does not provide a cart implementation or add-item contract. S-PAS-003 exposes an optional host callback; the isolated preview leaves it unavailable.
- This implementation remains Price-lock only. Vendor-funded Credit terms and behavior are not enabled.

### Deadline decision and order tracking contract gaps (Batch 5)

- The user task names `POST /pas/plans/{planId}/decision`; the approved workspace OpenAPI and API consumption mapping name `POST /pas/plans/{planId}/deadline-decision`. The injected adapter does not hardcode either URL. Resolve this route mismatch with the API owner before host integration. The documented request is exactly `{decision: EXTEND | REFUND}`, with `Idempotency-Key` and `X-Pin-Token`; the `200` response has no schema.
- Deadline extension fee, extension date/period, refund net amount, option eligibility, extension limit, and any associated consequences are not defined as response fields or rules in the API copy. The UI renders these values only from host-mapped context and disables an option until its required terms and availability are supplied. It calculates no fees/refunds and chooses no default option. The isolated preview supplies no decision terms and cannot submit a decision.
- `GET /pas/orders/{orderId}` has no documented `200` response schema. The injected order adapter uses a host-mapped `PasOrderTrackingData`; the workspace does not define product/vendor fields, delivery status/event schema, timestamps, delayed indicator, estimated delivery, delivery code, or code instructions. Those values are omitted when absent.
- Vendor contact action details/authorization are not specified. Contact and report callbacks are optional host-owned navigation/actions; the preview has neither. S-PAS-013 is not implemented in this batch, so Report a delivery problem is disabled in preview. The screen does not create delivery events, addresses, dates, code, QR, vendor actions, or tracking identifiers. Product imagery uses a host-supplied image only; no unrelated courier photo was added.
- The light Stitch references provide the common structural baseline. Dark variants contain materially different financial claims, statuses, delivery details, and layouts. This implementation retains one structure across themes and uses existing workspace palette/type styles. Stitch figures, extension terms, refund amounts, order events, fees, courier identity, delivery code, vendor contacts, escrow-release claims, and QR codes are not assumed to be production data.

### Credit repayment and report an order problem contract gaps (Batch 6)

- S-PAS-011 uses the host's mapping of `GET /pas/plans/{planId}`. The GET success schema is undocumented, so balances, installment amounts, dates, schedule entries, vendor context, and auto-debit display values must be host supplied. `POST /pas/plans/{planId}/repayments` documents `amountKobo`, `Idempotency-Key`, and `X-Pin-Token`, but no success response schema. The feature sends only the host-provided amount; it parses no display labels and calculates no balance, interest, fee, penalty, or schedule. The injected host owns PIN authorization and idempotency.
- O-009 remains open in the product PRD: legal confirmation is required before enabling vendor-funded credit. Repayment and auto-debit controls require host eligibility and an explicit legal-approval flag. The isolated preview supplies neither, and its repayment action is unavailable. No Instant Loan functionality is reused or implied.
- `PUT /pas/plans/{planId}/auto-debit` supports the documented `enabled` field; its success response schema is missing. Any credit auto-debit control is gated by host eligibility/legal approval and delegates authorization to the host.
- S-PAS-013 uses `POST /pas/orders/{orderId}/report`, whose documented request fields are `reason` and `description`. No approved reason enum/category list or success response schema is provided. The host must inject approved reason values and labels; if none are supplied, submission remains disabled. The current preview supplies no categories. Evidence attachments are omitted because the endpoint contract has no evidence field. No ticket ID, investigation duration, refund promise, or resolution guarantee is shown.
- The preview registers `/shop/credit/:id` and `/shop/orders/:id/report`; S-PAS-010 links to the report route with its order ID. Synthetic preview data contains no eligible credit plan and no report categories, so neither backend action can execute. Light and dark use the same hierarchy with workspace theme styling; Stitch-only fees, financial amounts, account selection, credit terms, order dispute allegations, evidence handling, and resolution commitments are not treated as approved production behavior.

The preview is marked NON-PRODUCTION and all data is synthetic. It has no network, authentication, payment, document, or backend client.
